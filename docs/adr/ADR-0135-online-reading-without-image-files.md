# ADR-0135 — Lectura online sin archivos de páginas

## Estado

Accepted, 2026-10-11. Sustituye la decisión de caché de disco de ADR-0134 para nuevas sesiones online. El usuario exige poder leer sin descargar capítulos ni necesitar espacio para guardarlos. Las migraciones y la recuperación de intentos anteriores se conservan.

## Decisión y alcance

- La lectura online descubre un plan de páginas y obtiene únicamente las páginas solicitadas. No crea una tarea de descarga, staging de imágenes, `.part`, `.page` ni CBZ. Los bytes pasan por memoria y por el mismo decodificador y límites que las descargas. El progreso sigue asociado al capítulo canónico.
- `OnlinePageProvider` distingue explícitamente un plan en memoria de `AcquisitionProvider`. `SourcePageService` valida ambos contratos. No se usa `get_pages()` de FMD2 para leer: ese método histórico inicia una adquisición que guarda archivos.
- FMD2 expone POST `/v1/reader`, GET `/v1/reader/{id}/pages/{ordinal}` y DELETE `/v1/reader/{id}`. Reutiliza los callbacks de listado, resolución dinámica e imagen del adaptador mediante tareas separadas del gestor de descargas. No registra tareas ni crea directorios. Comparte `FetchImage` con el descargador; la salida a archivo sigue en `DownloadImage`. Se liberan el documento del listado y los buffers de cada respuesta.
- Se conserva la allowlist pública y el token del core. Los identificadores, ordinales, referencias y tamaños se validan. Los hooks que requieren archivos se rechazan para lectura en memoria. Un rechazo de `OnBeforeDownloadImage` impide obtener la imagen online. No hay fallback silencioso a descarga, navegador externo o acceso alternativo.
- `DownloadTransport.fetch_memory` reutiliza el control de orígenes, secretos, redirecciones, tiempos, concurrencia, reintentos y `Retry-After` de las descargas. Evita completamente preflight, reserva y escritura de páginas. Se mantiene el límite de 64 MiB por página y dos respuestas del core en uso; la validación se ejecuta de una en una. Estos límites no son el consumo total del proceso: hay buffers de red, copia de bytes y decodificación raster.
- El navegador solicita imágenes con `cache: no-store`; la API devuelve `Cache-Control: no-store, private, no-transform`. La caché existente de blobs del lector usa RAM y respeta el ajuste de 16–500 MB. Se conserva la precarga configurada de 0–2 páginas y la ventana virtual del lector; no se adquiere todo el capítulo por adelantado.
- Una sola sesión online tiene el plan actual. Cambiar de capítulo libera el plan anterior; pausar, reabrir o cerrar no elimina progreso. `complete` en la API de esta sesión significa que el **plan** está establecido, no que se descargaron todas las imágenes. `ready_pages` contiene ordinales que pasaron validación en la sesión. Guardar progreso exige una página validada; el frontend espera además que la imagen se haya mostrado.
- El CBZ publicado mantiene prioridad en metadata e imágenes. Su verificación y lectura no cambian. Las descargas opcionales conservan staging, intentos durables, reserva de disco, validación, generación atómica y ComicInfo.xml.
- Al arrancar se recupera y retira únicamente la caché de disco del prototipo anterior con sus comprobaciones de ownership. No se eliminan CBZ, biblioteca ni progreso. Un namespace ambiguo o un proveedor sin reconciliar conserva sus archivos y registra el bloqueo; no deshabilita la nueva lectura en memoria.
- La reserva general de descargas de 512 MiB permanece. Una base ya migrada, íntegra y con esquema e historial verificados puede arrancar con el espacio necesario para recuperación de SQLite y un margen de 16 MiB para metadata. Una instalación nueva, una migración pendiente o una medición de espacio no verificable conserva el preflight anterior. Una aplicación instalada, preferencias, metadata, registro y progreso siguen utilizando disco; no se promete un equipo con cero bytes libres.
- En búsqueda, `Leer online` registra el capítulo canónico sin crear descargas y abre el lector React existente. `Descargar manga completo` añade todos los capítulos con referencia que devuelve la fuente, en lotes secuenciales de hasta 100. Reutiliza la creación idempotente de trabajos. Si un lote falla, los anteriores permanecen en cola y reintentar reutiliza los trabajos existentes.

## Verificación y límites

La aceptación Windows usa exclusivamente un módulo sintético autorizado en loopback. Un plan de 10.000 páginas cuyo tamaño conjunto estimado supera 2 GiB solicita solo primera y última página, crea cero archivos de imagen y cero trabajos de descarga, no reserva disco y conserva progreso al reabrir. En el mismo motor se comprueba una descarga explícita de tres páginas. La regresión anterior mantiene ocultación de archivos durante callback, generación, recuperación y liberación de staging.

La descarga completa comprende el catálogo que entrega la fuente; no garantiza capítulos que la fuente no lista o permite obtener. Falta validar el recorrido visual completo en el navegador de la aplicación y actualizar el instalador. El menú de descarga dentro del visualizador, navegación entre capítulos online y recuperación automática de un plan perdido al reiniciar el proveedor continúan en H3–H5. No se certifican fuentes reales a partir de fixtures. El sistema operativo puede paginar memoria por su propia gestión; Yomira no guarda las imágenes online en archivos.
