# ADR-0078 — Persistencia atómica del manifest de DownloadJob

## Status

Accepted — decisión de arquitectura aprobada tras revisiones independientes de seguridad y arquitectura. Esta aceptación no se atribuye al usuario. La implementación de K093 y su verificación backend quedaron completadas el 2026-09-27; K094 conserva la reconciliación tras interrupciones y K096 el cableado del recovery guard y el readiness gate.

## Context

K092 define un formato JSON v1 puro, determinista y acotado; K093 debe persistirlo en filesystem y K094 reconciliará DB, manifests y archivos después de una interrupción ([ADR-0076](ADR-0076-versioned-job-manifest.md)). ADR-0035 establece que `temporary_path` es relativa bajo `YomiraData/temp/` y única mientras esté registrada. ADR-0077 exige preservar su grafía original, imponer unicidad global mediante `casefold()` y no sobrescribir destinos existentes.

La publicación en filesystem y el commit SQLite son operaciones independientes: no forman una transacción distribuida. Windows también distingue la creación exclusiva de un archivo de la sustitución de un manifest existente. K093 necesita una ruta fija, un protocolo de publicación verificable y límites explícitos para las rutas resultantes.

## Decision

### Ubicación y representación

- Cada manifest de job se guarda en `<data_root>/database/manifests/<job_id>.json`, donde `job_id` usa el UUIDv4 canónico minúsculo definido por ADR-0076. Los archivos de staging y backups se crean en ese mismo directorio y volumen; no se permite fallback a copia entre volúmenes.
- `data_root` es la raíz absoluta resuelta de ADR-0045. Si la configuración apunta mediante symlink/junction a una raíz local existente, el destino resuelto se canoniza una sola vez y se usa para DB, temp, manifests y mutex; reparse points dentro de esa raíz canónica se rechazan según esta ADR. K093 solo admite volúmenes Windows locales fijos o removibles; raíces UNC, unidades de red y volúmenes desconocidos quedan fuera de soporte.
- La serialización, incluidos sus límites, termina antes de iniciar I/O. El escritor rechaza el objeto o los bytes completos si no cumplen ADR-0076; nunca trunca ni divide un manifest.

### Staging y publicación

- El escritor crea el archivo de staging con nombre único y creación exclusiva en el directorio final. Escribe todos los bytes, ejecuta `flush` y `fsync`, cierra el handle y verifica que el digest leído del staging coincide con el digest de los bytes serializados. También vuelve a parsear los bytes acotados y comprueba que el manifest es v1 válido para el mismo `job_id`.
- `save` en una creación inicial espera que el destino esté ausente y publica con `MoveFileExW` sin `MOVEFILE_REPLACE_EXISTING` ni `MOVEFILE_COPY_ALLOWED`. Si aparece un destino, la operación falla y lo conserva.
- `save` en una actualización requiere el digest esperado del manifest anterior y valida que sea SHA-256 hexadecimal minúsculo de 64 caracteres antes de I/O. Inmediatamente antes de reemplazar, compara ese digest con el destino: si el archivo falta o el digest no coincide, falla sin escribir ni sustituirlo y devuelve `DL_MANIFEST_STALE_SNAPSHOT`. Si el digest coincide, además exige que el destino sea v1 válido del mismo job; de lo contrario, falla sin reemplazarlo con `DL_MANIFEST_PERSIST_FAILED`. Una actualización válida usa `ReplaceFileW` con un nombre de backup único en el mismo directorio. Antes de invocar `ReplaceFileW`, valida el candidato exacto de backup: debe estar ausente, no ser reparse point y su estado debe poder comprobarse; ante existencia, ambigüedad o error de consulta, no llama a la API ni altera destino, candidato o staging. `save` devuelve el SHA-256 de los bytes leídos y verificados desde el destino final.
- Tras publicar una actualización, el escritor comprueba que el backup conserva el SHA-256 esperado del manifest previo; después vuelve a leer el destino con el límite de bytes de ADR-0076, valida el manifest y verifica su digest. Si el backup no coincide, la actualización falla con `DL_MANIFEST_STALE_SNAPSHOT`; conserva el backup, el destino y cualquier staging que aún exista para K094. `ReplaceFileW` consume el staging al completarse: en ese resultado el manifest nuevo queda en destino y el anterior en backup; no se recrea ni se elimina evidencia. El backup anterior solo puede eliminarse después de que ambas verificaciones terminen. Si el resultado de la API o la verificación es ambiguo, se conservan todos los candidatos que sigan existiendo; no se elige uno por timestamp ni se borra evidencia.
- Todas las publicaciones para el mismo job adquieren un mutex Win32 con nombre en el namespace `Global`. Para clasificar el volumen final de la raíz canonizada, primero obtiene la ruta de montaje con barra final mediante `GetVolumePathNameW(canonical_data_root)` y consulta `GetDriveTypeW(volume_mount_path)`; solo acepta `DRIVE_FIXED` o `DRIVE_REMOVABLE`. Esto sigue junctions y carpetas montadas hasta el volumen destino. El mutex deriva su nombre de SHA-256 sobre el `VolumeSerialNumber` y `FileId` de 128 bits obtenidos con `GetFileInformationByHandleEx(FileIdInfo)` para el handle de esa misma raíz, junto con el UUID canónico del job; aliases Win32 de la misma raíz en el mismo host comparten el mutex. Si `GetVolumePathNameW` o `GetDriveTypeW` falla, el tipo es distinto de `DRIVE_FIXED`/`DRIVE_REMOVABLE` (incluye `DRIVE_UNKNOWN`, `DRIVE_NO_ROOT_DIR` y `DRIVE_REMOTE`), la consulta de identidad falla o el identificador es incompleto, se falla cerrado con `DL_MANIFEST_PERSIST_FAILED` y etapa `root_identity` antes de iniciar transacciones o tocar páginas/manifests. La garantía de concurrencia entre procesos y sesiones es local al host; dos equipos que accedan concurrentemente a la misma raíz no están soportados.
- `JobManifestStore(data_root, data_root_identity, recovery_guard)` exige el objeto `DataRootIdentity` compartido de runtime y un callable `recovery_guard(job_id: UUID) -> None` de K094; no hay default ni fallback no-op en producción. `TemporaryPageStore` y `SQLiteDatabase` reciben el mismo objeto de identidad; los tres componentes fallan cerrado antes de I/O si falta. `DataRootIdentity` contiene la ruta canonizada y el par inmutable `(VolumeSerialNumber, FileId)` capturado una sola vez por el bootstrap; los componentes no capturan una identidad base independiente. Si un constructor recibe `data_root`, este debe ser absoluto y coincidir textualmente con `data_root_identity.canonical_path` después de normalizar separadores, componentes `.`/`..` y mayúsculas/minúsculas Windows, sin consultar ni resolver el filesystem. `SQLiteDatabase(path, data_root_identity)` recibe la ruta absoluta del archivo DB y debe comprobar, bajo esa misma normalización puramente léxica, que coincide con `<canonical_path>/database/yomira.sqlite3`. Estas comparaciones se hacen antes de crear directorios, abrir DB, adquirir mutex o tocar archivos. Una discrepancia o ruta no absoluta falla cerrado sin I/O de DB/filesystem. Tras esa comprobación, todas las rutas derivadas se construyen exclusivamente desde `data_root_identity.canonical_path`; nunca desde un argumento de ruta sin validar. Si una comprobación posterior detecta falta o cambio de identidad, la instancia compartida se invalida y todos los componentes fallan cerrado hasta reinicio, recovery K094 y gate K096. El callable retorna normalmente solo si el job quedó reconciliado y apto para operar; si el estado no puede resolverse, debe lanzar un error trazable de recovery y bloquear la operación. Omitir la identidad en `SQLiteDatabase` falla con `DB_CONNECTION_FAILED` y etapa `root_identity`; omitir identidad/guard en `JobManifestStore` o suministrar un guard no callable falla con `DL_MANIFEST_PERSIST_FAILED` y etapa `root_identity`/`recovery_guard_configuration` respectivamente. El guard debe ser idempotente y reanudable después de una interrupción en cualquier punto: las acciones durables repetidas no pierden datos; si una contradicción sigue siendo ambigua, conserva todos los candidatos y falla cerrado sin escoger por fecha ni sobrescribir contenido. Los tests aislados de K093 pueden construir una identidad para su raíz temporal e inyectar un guard no-op local; las pruebas de contrato deben verificar la identidad compartida, la llamada, una nueva invocación tras fallo previo y el fail-closed ante excepción. El guard no puede adquirir de nuevo el mutex de ese job ni transferir la ejecución a otro hilo.
- `lock_job(job_id)` es un context manager síncrono que espera como máximo 5000 ms. `WAIT_TIMEOUT`, `WAIT_FAILED` o fallo de creación/acceso producen `DL_MANIFEST_PERSIST_FAILED` en etapa `job_mutex_wait` antes de iniciar transacciones DB o I/O de página/manifest; K093 no reintenta. `WAIT_ABANDONED` indica que el owner anterior terminó abruptamente y concede propiedad al waiter. No se libera ni se expone el lock hasta que `recovery_guard` termina bajo ese mismo mutex; todo error o estado irresoluble bloquea la operación. El guard también se ejecuta en cada adquisición externa normal, de modo que un segundo waiter que reciba `WAIT_OBJECT_0` tampoco publica sin recovery. En reentrada del mismo hilo `save` conserva la adquisición externa y el guard corre una sola vez por sección crítica exterior. El arranque ejecuta la reconciliación K094 antes de aceptar jobs; K096 mantiene el Job Manager no listo hasta que ese gate pase. La adquisición, sección crítica y liberación ocurren en el mismo hilo del sistema. El caller ejecuta en ese mismo hilo la transacción DB breve, su commit/cierre y la llamada a filesystem; no usa `await` ni transfiere el lock a otro worker. `save` conserva el lock desde antes de comprobar el digest hasta verificar destino/backup y cerrar la operación. `TemporaryPageStore.create(temporary_path)` es una primitiva filesystem e inicia solo después de confirmar la reserva DB. Si otro proceso Yomira publicó primero, el digest esperado deja de coincidir y la actualización falla con `DL_MANIFEST_STALE_SNAPSHOT`. Ningún lock cubre ediciones manuales ni procesos ajenos que ignoren este protocolo.

- Antes de cada nueva transacción SQLite y cada operación filesystem, el componente vuelve a resolver la raíz y compara su identidad con el único objeto de bootstrap; si la identidad no está disponible o difiere, invalida el runtime/store/pool y falla cerrado (`DB_CONNECTION_FAILED` para la DB; `DL_MANIFEST_PERSIST_FAILED` para los stores, etapa `root_identity`). No se continúa hacia otra unidad que haya tomado la misma letra o punto de montaje; hace falta reiniciar, ejecutar K094 sobre el medio identificado y volver a pasar el gate de K096 antes de reanudar. Esto también aplica a volúmenes removibles: la raíz no puede cambiar de identidad durante la sesión.

### Alcance de atomicidad

- La garantía de producto es que la terminación del proceso durante la escritura no publique bytes parciales como un manifest válido en la ruta definitiva. El staging se completa y verifica antes de llamar a la operación de publicación; los candidatos completos se conservan cuando no puede determinarse el resultado.
- K093 promete atomicidad de publicación frente a terminación del proceso; no promete durabilidad ante pérdida de energía. `flush`/`fsync` y las APIs de Windows no se presentan como garantía de persistencia de metadatos de directorio o del medio físico después de una pérdida de energía.
- K093 no reintenta operaciones del filesystem. K108 definirá y aplicará backoff acotado solo para sharing violations/bloqueos transitorios de operaciones filesystem en Windows; no aplica al mutex nombrado del job (`WAIT_TIMEOUT`, `WAIT_FAILED` ni errores de `job_mutex_wait`), que fallan sin reintento según este ADR. Permisos, disco lleno, rutas inválidas, resultados ambiguos y conflictos de destino no se reintentan aquí.

### Frontera SQLite/filesystem y recuperación

- K093 no declara SQLite y filesystem una sola transacción. Un fallo o crash puede dejar un manifest desfasado respecto de SQLite o candidatos de publicación pendientes. No se altera ni sobrescribe contenido para hacerlos coincidir automáticamente.
- SQLite y filesystem no forman una transacción distribuida. El caller adquiere `lock_job(job_id)` antes de abrir la transacción DB y lo mantiene hasta completar la publicación correspondiente. Las transacciones DB permanecen breves y se confirman/cierran antes de cualquier escritura, flush/fsync, lectura de verificación, renombrado o reemplazo de archivos: primero se confirma la reserva SQLite de `temporary_path`, luego se cierra la sesión y solo entonces se llama a `TemporaryPageStore.create`; para un manifest, se confirma el estado DB, se obtiene el snapshot en una transacción de lectura breve, se cierra la sesión y luego `save` publica bajo el mismo lock. Si cualquier paso falla, no se informa éxito ni se revierte heurísticamente el otro almacén. Un crash entre commit SQLite y publicación puede dejar los almacenes divergentes; K094 clasifica DB, manifest, backup y staging. Una edición DB que ignore el lock y aún no se refleje en un manifest no puede detectarse por el CAS del archivo. El estado del job no se declara `COMPLETED` por la mera existencia del manifest.
- K094 verifica DB, manifest, backup y staging y decide la clasificación conforme a ADR-0068. Una contradicción no explicada se trata como fallo cerrado; no se resuelve escogiendo el archivo más nuevo ni reconstruyendo contenido por heurística de fechas. El recovery parcial debe poder reanudarse tras otro cierre abrupto: conserva evidencia ambigua y no elimina ni sobrescribe candidatos hasta demostrar que la transición es segura.
- En producción, solo el composition root protegido por K096 construye `JobManifestStore` y le inyecta `recover_job` del mismo `RecoveryCoordinator` que ejecuta la reconciliación de arranque. Los no-op solo se permiten en tests unitarios aislados. K096 no declara listo el Job Manager si no pasó la reconciliación de arranque con ese coordinator real. No se inspecciona por reflexión un callable opaco para inferir su identidad; se verifica el wiring del composition root.

### Resolución y límites de rutas

- `temporary_path` permanece como ruta POSIX relativa bajo `<data_root>/temp/`; no se almacena ruta absoluta en DB o manifest. El resolver canoniza `data_root`, combina y resuelve la ruta y comprueba contención real antes de cada acceso.
- Se rechaza cualquier reparse point en `<data_root>/temp`, sus componentes y el destino de página, y en `<data_root>/database`, `<data_root>/database/manifests`, los destinos de manifest/staging/backup y el destino de página; no se permiten aliases internos aunque permanezcan dentro de la raíz canónica. Antes de abrir o migrar SQLite, `SQLiteDatabase` rechaza también volúmenes no-locales y reparse points en el directorio `database`, `yomira.sqlite3` y sus sidecars `yomira.sqlite3-wal`, `yomira.sqlite3-shm` y `yomira.sqlite3-journal`; falla con `DB_CONNECTION_FAILED` en `path_preflight` sin abrir la base ni iniciar backup/migración. Después de crear directorios necesarios, el resolver vuelve a canonicalizar y comprobar cada componente antes de abrir destinos. La comprobación no elimina el TOCTOU si una herramienta externa muta concurrentemente la estructura entre validación y operación. ADR-0044 documenta un riesgo análogo para rutas de biblioteca, pero no proporciona por sí misma protección para estos directorios. El contrato supone que ninguna herramienta externa edita concurrentemente `<data_root>`; todas las instancias Yomira que comparten la raíz deben usar el mutex `Global` de esta ADR.
- K093 mide en unidades de código UTF-16 cada ruta absoluta completa que entregará a la API de filesystem: destino de página, manifest, staging y backup, incluida la raíz y el nombre final generado. Admite hasta 259 unidades, excluido el NUL terminador; rechaza 260 o más antes de escribir. No usa ni habilita el prefijo extendido `\\?\` en K093. El diagnóstico registra el conteo, no la ruta literal.
- Los destinos de páginas se crean exclusivamente (`CREATE_NEW` o modo `xb`). Nunca se abren con truncamiento ni se reemplazan. La existencia del destino en disco es un conflicto, aunque la base no tenga aún una fila que lo registre.

### Identidad y migración global

- Antes de calcular o usar claves, K093 verifica que `unicodedata.unidata_version == "16.0.0"`, correspondiente al runtime fijado Python 3.14.7. Si difiere, bloquea el preflight y las reservas hasta una migración formal. La clave persistida de una ruta no nula es `temporary_path.casefold()` con esos datos Unicode. La clave es interna para unicidad: no reemplaza, normaliza ni se muestra en lugar de la ruta original.
- K093 persiste la clave derivada como `temporary_path_key`, asociada a la misma fila y actualizada en la misma transacción que `temporary_path`, con unicidad global para valores no nulos. `NULL` no reserva ruta. No recalcula claves silenciosamente. El caller confirma primero esa reserva en SQLite y solo entonces solicita la creación exclusiva del archivo. Si la creación falla o su resultado es incierto, conserva la reserva, no declara éxito ni elimina candidatos automáticamente; K094 los clasifica y reconcilia.
- Antes de crear la tabla TEMP, la migración `0016` establece y verifica `PRAGMA temp_store=FILE`, lee `PRAGMA compile_options` y fija el tamaño sugerido de cache TEMP con `PRAGMA temp.cache_size=-2048`; verifica cada valor antes del scan. Exige `temp_store=1`, que `TEMP_STORE` no sea `3` y `temp.cache_size=-2048`; cualquier incompatibilidad o lectura/escritura no disponible aborta antes del scan, de la tabla TEMP y de DDL permanente. La versión runtime mínima de ADR-0025 incluye `octet_length()`. El TEMP reside en disco y `-2048` solicita aproximadamente 2048 KiB para su page cache bajo el page cache integrado fijado; no es una cota de memoria de todo el proceso. El preflight no modifica `SQLITE_LIMIT_LENGTH`, que también limita otros campos/filas. Primero transmite únicamente `(job_id, ordinal, byte_length)` usando `octet_length(temporary_path)`; SQLite obtiene la longitud de los metadatos del registro sin cargar el contenido de la columna. Si excede 4096 bytes, reporta `(job_id, ordinal)` y aborta antes de leer el texto o calcular `casefold()`. Si pasa, consulta y materializa solamente ese `temporary_path` individual, acotado a 4096 bytes; no selecciona `remote_reference` ni otra columna de texto sin límite. Un `remote_reference` mayor de 4096 bytes no bloquea ni se materializa en el preflight. Solo se aceptan rutas de hasta 259 unidades UTF-16; las mayores se reportan por identidad y abortan antes de DDL permanente. Rutas aceptadas cuya ruta absoluta resuelta resulte demasiado larga fallan de forma trazable antes de abrirlas.
- Tras esas comprobaciones, el preflight calcula las claves con Unicode 16.0.0 y las inserta en una tabla TEMP con índice único. Ante una colisión, informa ambos `(job_id, ordinal)` y aborta antes de cambiar esquema, filas, rutas o archivos. Si no hay colisiones, agrega y rellena `temporary_path_key` y crea su índice único. Conserva las rutas originales byte por byte en su representación UTF-8.
- La migración usa el backup verificado y las comprobaciones de esquema/integridad ya exigidos por las reglas de persistencia. Cambiar algoritmo o versión Unicode exige nuevo preflight y migración formal, como establece ADR-0077.

### Errores y trazabilidad

- `DL_MANIFEST_PERSIST_FAILED`: staging, flush, verificación o publicación del manifest falló; no se informa éxito y se conserva evidencia según el estado de la operación.
- `DL_MANIFEST_STALE_SNAPSHOT`: el destino del manifest está ausente o su digest no coincide con el esperado para una actualización; no se escribe sobre el destino.
- `DL_TEMPORARY_PATH_CONFLICT`: la clave global ya está registrada o el destino exclusivo ya existe; no se reemplaza ningún archivo.
- `DL_TEMPORARY_PATH_UNAVAILABLE`: raíz inaccesible, escape de contención, cualquier reparse point bajo los directorios administrados, ruta demasiado larga o destino no disponible.
- El registro incluye `trace_id`, `job_id`, `stage`, tipo de causa y, para rutas, el número de unidades UTF-16. No incluye secretos, contenido del manifest ni la ruta completa del usuario. K093 no reintenta; K108 define después la política de locks transitorios.
- K093 registra estos identificadores en `ErrorCode` y `docs/ERROR_CODES.md`, con severidad, etapa, retryability y acción segura coherentes con este contrato.

## Alternatives Considered

- Escribir directamente al destino: podría hacer visible un JSON parcial y destruir el último manifest válido; se rechaza.
- Usar `os.rename` para actualizar el destino: en Windows el destino existente provoca `FileExistsError`; no proporciona la semántica de reemplazo requerida.
- Usar `MoveFileExW` con `MOVEFILE_REPLACE_EXISTING` para todas las publicaciones: permitiría sustituir un destino inesperado, contrario a la creación exclusiva de páginas y al control de identidad del manifest.
- Guardar rutas absolutas o normalizar `temporary_path`: acopla datos a una raíz concreta o altera una identidad ya persistida; se rechaza por ADR-0035/0077.
- Resolver contradicciones por fecha de modificación: no prueba que el contenido sea íntegro ni que corresponda a la última transacción; se rechaza por ADR-0068.
- Prometer recuperación tras pérdida de energía: no está garantizada por este protocolo y queda fuera del alcance de K093.

## Positive Consequences

- Un manifest se valida y limita antes de I/O; la ruta final nunca recibe una escritura progresiva.
- La creación exclusiva y la unicidad global protegen tanto contra carreras de DB como contra archivos existentes no registrados.
- Un resultado ambiguo conserva material suficiente para que K094 diagnostique sin sobrescribirlo.
- El límite absoluto es medible y rechazable antes de abrir archivos, también para staging y backup.

## Negative Consequences

- Una raíz larga puede volver inadmisible una ruta que el volumen aceptaría con APIs extendidas; K093 la rechaza deliberadamente.
- El backup y el staging pueden coexistir temporalmente y consumir hasta el tamaño acotado por ADR-0076 por cada candidato.
- La actualización no ofrece una transacción distribuida; un crash puede requerir que K094 marque el job como inconsistente.
- Un runtime con otra versión de tablas Unicode requiere detener las reservas de rutas hasta ejecutar el preflight/migración aprobado.

## Failure Modes

- Disco lleno o error de escritura/flush: no reemplazar el manifest anterior; conservar o clasificar el staging propio sin borrar archivos fuente.
- El primer publish encuentra destino existente: fallar con `DL_MANIFEST_PERSIST_FAILED`; no cambiar a modo reemplazo.
- El destino existente no es v1 válido o su `job_id` no coincide: no reemplazarlo; conservarlo para diagnóstico.
- El digest esperado de una actualización no coincide o el manifest desapareció: fallar con `DL_MANIFEST_STALE_SNAPSHOT`, sin tocar el destino ni el backup.
- `MoveFileExW` devuelve resultado ambiguo o falla la verificación después de publicar: conservar el destino final si el movimiento se completó y cualquier staging que aún exista; si el movimiento no se completó, conservar el staging y dejar intacto el destino. El movimiento completado consume staging, por lo que no se recrea. K094 clasifica lo que permanezca; K093 no reintenta.
- `ReplaceFileW` devuelve resultado ambiguo o el digest final no coincide: conservar backup, destino y cualquier staging que siga existiendo; si la sustitución atómica consumió staging, backup y destino conservan las dos versiones completas. K094 clasifica candidatos y DB sin decidir por timestamp.
- El backup de una actualización no coincide con el digest esperado: devolver `DL_MANIFEST_STALE_SNAPSHOT` y conservar cada candidato que siga existiendo; si `ReplaceFileW` completó, el backup y el destino preservan respectivamente los bytes anteriores y nuevos. No recrear staging.
- Colisión de `casefold()` durante migración: reportar las dos identidades y abortar antes de DDL permanente o cambios de datos.
- Resolución fuera de `<data_root>/temp/` o ruta de 260+ unidades UTF-16: rechazar antes de escribir y emitir el error estable correspondiente.
- Mutación externa concurrente de symlink/junction/reparse point después de la comprobación: la operación puede fallar o quedar fuera del control del proceso; no continuar si el handle/validación detecta el cambio y registrar el límite TOCTOU documentado en esta ADR.
- `TEMP_STORE=3`, lectura de compile options no disponible o cache TEMP distinta de `-2048`: abortar el preflight antes del scan y de DDL permanente.

## Verification Requirements

- Primer publish: validar bytes y digest; un destino preexistente permanece byte por byte intacto.
- Creación inicial: verificar que el destino esté ausente y no sobrescribirlo si aparece.
- Actualización CAS: manifest v1 válido del mismo job, `expected_sha256` bien formado y coincidente inmediatamente antes del reemplazo; rechazar sin escritura ante digest distinto o archivo ausente, verificar que el backup conserve ese digest y comprobar el digest final. Ante una verificación incierta se preserva cada candidato que siga existiendo; si `ReplaceFileW` completó, backup y destino mantienen las versiones anterior y nueva, aunque staging haya sido consumido. Dos procesos Yomira sobre el mismo `data_root` y job se serializan con el mutex `Global`; una segunda actualización basada en el digest anterior debe fallar como snapshot obsoleto.
- Los fault tests usan seams estrechos en `app.persistence.manifest_store`: `_move_file_ex_win32(source_path, destination_path)` fija los flags seguros de `MoveFileExW`; `_replace_file_win32(replaced_path, replacement_path, backup_path)` encapsula `ReplaceFileW`; `_read_manifest_bytes(path, *, max_bytes)` realiza cada lectura de verificación con límite. No son puntos de extensión del producto. Fault injection en creación, escritura, flush/fsync, lectura de verificación y ambas APIs Win32, tanto antes de mutación como cuando la API ya mutó el filesystem pero el caller recibe un resultado de error ambiguo; terminación de proceso en cada frontera de publicación; no exponer JSON parcial y conservar todos los candidatos que sigan existiendo para K094. Tanto `MoveFileExW` como `ReplaceFileW` consumen staging al completarse; en ese caso el destino conserva los bytes nuevos, y el backup de actualización conserva los anteriores. No recrear ni borrar evidencia. Probar también fallo de lectura/verificación posterior a `MoveFileExW`: no informar éxito ni recrear el staging consumido, y dejar el manifest completo en el destino para K094. Si el candidato de backup existe o es reparse point, verificar que `ReplaceFileW` no se llama y que staging, destino y candidato permanecen intactos.
- Pruebas de ruta en límites 259/260 UTF-16, incluyendo caracteres suplementarios, raíz larga, escapes y cualquier symlink/junction/reparse point bajo `<data_root>/temp`, `<data_root>/database`, `<data_root>/database/manifests`, el archivo SQLite y sus sidecars WAL/SHM/journal; comprobar que no se abre ni trunca el destino rechazado ni se inicia backup/migración. Probar `GetVolumePathNameW`/`GetDriveTypeW` sobre raíces normales, roots anidados, junctions y carpetas montadas; rechazar si falla una consulta, si el tipo no es `DRIVE_FIXED` o `DRIVE_REMOVABLE`, o si la identidad física es fallida/incompleta. Simular que un volumen removible desaparece y otra identidad ocupa el mismo path antes de sesión DB y entre commit DB y filesystem; comprobar que no se escribe en el volumen sustituto. Comprobar que raíces UNC/unidades de red se rechazan antes de persistencia y que aliases locales resueltos comparten el mutex.
- Migración 0016: verificar `PRAGMA temp_store=1`, aceptar compile option ausente/0/1/2 y rechazar `TEMP_STORE=3`; verificar `PRAGMA temp.cache_size=-2048` antes del scan. El query inicial debe proyectar solo `job_id`, `ordinal` y `octet_length(temporary_path)`, reportar una ruta histórica de más de 4096 bytes por identidad sin seleccionar su texto, y permitir `remote_reference` de más de 4096 bytes sin leerlo. Comprobar que el límite SQLite de la conexión queda intacto en éxito y error. Probar una ruta de 260 unidades UTF-16 y colisión global ASCII/Unicode, dejando intactos DDL permanente, filas y archivos ante rechazo. El caso sin colisiones preserva cada ruta y rechaza reservas duplicadas.
- Errores de disk full, permiso denegado, destino existente, reparse point, mutex ocupado/abandonado y lock persistente conservan datos y emiten código, etapa y trazabilidad; probar timeout, abandono, recovery_guard bajo lock, dos waiters en cola, guard también en el lock implícito que adquiere `save` cuando no hay `lock_job` externo, adquisición recursiva del mismo hilo, serialización entre procesos y que K093 no reintenta.
- Tests de K093 construyen/reciben el mismo `DataRootIdentity` para SQLite, manifest y temporary stores; un constructor que recibe un `data_root` distinto al `canonical_path` debe rechazarlo antes de cualquier I/O de DB/filesystem, aunque el objeto de identidad sea válido. Tras simular que su proveedor reporta otra identidad, cada componente bloquea I/O y sesiones. También prueban el cambio entre commit de reserva SQLite y creación/publicación de archivo, sin escribir en el medio sustituto. K096 verifica que el bootstrap inyecta exactamente la misma instancia (`is`) a SQLite, `JobManifestStore` y `TemporaryPageStore`, que la invalidación de esa instancia bloquea a los tres y que el readiness gate no pasa si falta o falla el coordinator real.
- Una excepción del guard bloquea publicación y una adquisición posterior vuelve a ejecutar el guard antes de operar. K094 termina el proceso después de cada mutación durable de recovery, reinicia y reanuda el guard; verifica que converge de forma segura, no descarta candidatos y no sobrescribe contenido ambiguo.
- Test de runtime confirma `unicodedata.unidata_version == "16.0.0"` antes de calcular claves; otra versión bloquea el preflight y reservas hasta migración formal.
- K094 añade fault tests de clasificación de target/backup/staging frente a DB y termina/reanuda el recovery tras cada mutación durable; K108 añade Windows tests de retries acotados únicamente para sharing/lock transitorios.

## Reversal Strategy

Cambiar ubicación, secuencia de publicación, APIs Windows, límite de ruta, garantía de atomicidad, identidad Unicode o tratamiento de conflictos requiere nueva ADR. La migración de identidad siempre debe hacer backup y preflight global antes de cualquier cambio permanente. Nunca resolver colisiones o candidatos ambiguos mediante normalización, renombrado o eliminación automática.
